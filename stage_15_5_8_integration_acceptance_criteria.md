# Stage 15.5.8 — Future Persistence Integration Acceptance Criteria

These criteria apply to a future read-integration stage (proposed Stage
15.5.9). They are not claims that integration has been implemented. Read
hydration must remain separate from database write persistence.

## Successful startup

- [ ] SQLite opens through the existing SQL-plugin pool.
- [ ] Foreign-key verification and schema migration complete before repository
      data is exposed.
- [ ] Product, Inventory records/batches, Sales drafts, Delivery drafts,
      completed Sales, received Deliveries, and Activity are all loaded.
- [ ] A single coordinator validates the complete candidate state before
      publishing it; no partially loaded collection is visible.
- [ ] No Product/Inventory or draft reference is silently dropped, recreated,
      or substituted from demo/current data.
- [ ] Product and Inventory arrays preserve IDs, hierarchy, associations,
      nullable values, quantities, batch identity, and stable ordering.
- [ ] Active Sale and Delivery drafts are distinguishable from terminal or
      completed records. Only active `status = "draft"` records establish
      Product-wide locks.
- [ ] Completed Sale and received Delivery records retain their historical
      payloads independently of current catalog/stock rows. All snapshot
      contract decisions are explicit and tested; unresolved JSON remains
      opaque rather than being cast to a domain snapshot.
- [ ] Activity IDs, event type, timestamp, ordering, nullable actor fields and
      stored event payloads remain faithful. Activity is not regenerated by
      hydration.
- [ ] Loading draft data causes no stock reservation, quantity change, batch
      creation, or Activity event.
- [ ] Demo data is available only through an explicit test/development path;
      the production/default initialization path does not seed it.
- [ ] Existing unsaved-data messaging remains truthful until a separate
      persistence-write stage is completed.

## Failure scenarios and expected behavior

| Scenario | Expected observable behavior |
|---|---|
| Plugin database load fails | Show a blocking initialization error; do not expose demo or partially initialized operational state. |
| Foreign-key verification fails | Stop before repository reads; surface the failure. Preserve the existing partial-connection cleanup behavior and report cleanup failure explicitly. |
| Migration fails | Stop before repository reads and show the initialization error. Do not claim the app is ready or fall back to demo state. |
| Any repository query fails | Show a load error identifying the failed phase/repository; publish none of the candidate state. |
| Candidate-state relationship or snapshot validation fails | Fail the whole load; do not discard individual rows or patch them with current Product/Inventory data. |
| One query finishes while another is pending | Keep the application behind its loading gate; do not dispatch or enable actions until all required reads and validation succeed. |
| Empty but valid database | Publish genuinely empty persisted collections. Do not insert or display demo Products/Inventory as persisted records. |
| Retry after initialization/load failure | Retry explicitly; success transitions once to ready, and failure remains visibly failed. No stale partial candidate is reused. |
| Database changes concurrently during multi-query startup | Either prove a shared read snapshot was used, or reject this as unsupported and document/enforce a no-writer startup window. `Promise.all` alone is not evidence of snapshot consistency. |

## Data-integrity and business-rule checks

- [ ] Inventory records and batch associations match loaded Product/Variant
      IDs; packaging stock and batch pricing refer to the correct Variant.
- [ ] Distinct batches remain distinct even when batch numbers match but
      expiry dates differ. Missing batch numbers and nullable expiry values
      remain intact.
- [ ] Sale draft item IDs, batch association, Inventory record, Product,
      Variant and packaging references are checked against the loaded live
      state. Draft hydration does not reserve or deduct stock.
- [ ] Delivery draft items retain Product/Variant/packaging IDs, batch number,
      expiry, quantity, optional prices and item order. Draft hydration does
      not create Inventory batches, change stock, or write Activity.
- [ ] Every `sale_drafts.status = 'approved'` row is consistent with its
      completed Sale relationship; completed Sale event references resolve to
      the corresponding stored Activity row. Any relational mismatch fails
      hydration instead of dropping a record.
- [ ] Received Delivery rows remain distinct from drafts and link to their
      stored receipt Activity event. Cancelled Delivery history comes from its
      cancellation Activity snapshot; no cancelled live draft row is invented.
- [ ] Historical Sale/Delivery/Activity records are not rejected merely
      because a referenced Product, Variant, Batch, or Inventory record is no
      longer live.
- [ ] Product-wide active-draft locks are present before Product or Inventory
      workflows become available. Product deletion never cancels drafts to
      bypass a lock.
- [ ] Existing FEFO allocation, batch identity, packaging hierarchy and
      conversion rules are unchanged.
- [ ] Reads do not execute workflow reducers, database writes, stock
      mutations, Activity creation, cancellation, or approval.
- [ ] Existing focused Product, Inventory, Activity, Sales, Delivery, draft,
      and workflow tests remain passing. The new combined loader tests use an
      isolated database initialized with the actual Migration 001 SQL.
- [ ] At least one isolated end-to-end Tauri IPC startup/read smoke test
      exercises the real registered read command against a temporary
      database; unit tests with mocked `invoke` remain useful but do not replace
      this check.
- [ ] Money values continue to use checked conversions. Unsafe or
      non-round-trippable persisted values fail explicitly; no rounding or
      truncation is introduced. Safe-range validation remains a prerequisite
      for future money writes.

## Required focused tests

- Empty persisted database and normal populated state.
- Multiple Products, Variants, packaging levels, Inventory records, and
  batches with stable associations/order.
- Draft statuses and item ordering; nullable Sale metadata and nullable
  Delivery draft headers; all decisions about null-to-domain mapping.
- Approved Sale ↔ Sale draft ↔ Activity linkage; received Delivery ↔ Activity
  linkage; cancelled Sale drafts remain cancelled and cancelled Delivery
  history remains in Activity.
- Product deletion/historical records: old snapshots survive without live
  Product/Inventory joins.
- Malformed/unknown snapshot contracts and metadata mismatch fail explicitly
  or remain opaque according to the agreed contract; never repair silently.
- Any one repository error, initialization failure, and candidate validation
  error results in no partial ApplicationState publication and no demo
  fallback.
- Active-draft locks are effective immediately after successful hydration.
- Before/after database reads show no change to Inventory quantities, batches,
  Sales/Delivery lifecycle, or Activity rows.
- Existing workflow tests prove drafts still do not mutate stock and that
  approval behavior remains unchanged. Database transaction atomicity is
  tested later with the write-persistence stage, not inferred from read tests.

## Exit conditions

Read integration is complete only when all of the following are true:

1. The Sales and Delivery mapping/serializer decisions are documented and
   covered by tests, or opaque persisted models are retained without
   pretending they are current domain snapshots.
2. Draft readers restore the required lifecycle and metadata from Migration
   001 without writes.
3. Startup waits for migration and complete repository loading before
   exposing operational state.
4. Empty state, query errors, migration errors, malformed data, and retry
   behavior match the failure table above; there is no silent demo fallback.
5. No state is partially published, and active draft locks are available
   before user interactions.
6. Existing Sales, Inventory, Receive Delivery, Product, Activity, FEFO, and
   packaging tests remain green; focused new tests cover cross-repository
   hydration.
7. No normal database is used for tests or migration validation.
8. The UI/status does not imply database durability for workflow changes until
   write persistence is implemented and separately verified.
9. Sales and Receive Delivery database approvals are not claimed atomic until
   a later write-persistence stage proves transaction commit/rollback behavior
   through the existing transaction boundary.
