# Stage 15.5.13 — ApplicationState Field Mapping

This table maps every current `ApplicationState` property to the Stage 15.5.12 loader result. “Direct” means the current workflow/domain value can be populated without reconstructing business data; it does not imply database writes are implemented or that every original SQL representation is retained.

| `ApplicationState` field | Current initial/runtime source | Loader source and proposed mapping | Losslessness / persistence-only data | Demo or in-memory dependency | Required action before integration |
|---|---|---|---|---|---|
| `products: productStructure[]` | `createInitialApplicationState()` starts from `demoProducts`; reducer updates it in memory. | `ApplicationDataAssembly.products` → replace the field. | Product IDs, names, descriptions, generic names, manufacturer/category, variant IDs/names, registration metadata, thresholds, packaging hierarchy/IDs/names/prices and relationships map to the existing model. Repository ordering becomes array order. Product repository maps SQL NULL optional fields to absent properties and does not expose raw position numbers, so null-vs-absent and numeric position values cannot be recovered from this loader. | **Yes:** initial state is demo-backed. Later Product changes are memory-only. | Replace demo values only after a complete load; do not merge. Accept array order/optional absence for current Product behavior or revise repository DTOs first if exact SQL positions/NULLs are required. The provided shape supports display/edit logic, but edits are not durable. |

## Additional loader result data

`persistenceLimitations` is metadata about source-repository losses: Product/Inventory repositories omit original SQL NULL distinctions and numeric position values, and Sales/received-Delivery DTOs do not expose header positions. It is not an `ApplicationState` domain field. Preserve it in diagnostics or the integration report rather than silently treating it as business data.

## Exact downstream consumers

| State collection(s) | Current consumer behavior |
|---|---|
| Products + Inventory records + batches | Products and Inventory pages view/edit current data; Sales/Delivery pages resolve active-draft references; Dashboard computes stock/expiry alerts. |
| Sale drafts | Sales page resumes/edits/approves drafts; Dashboard counts and navigates to active drafts; Product and Inventory operations use drafts for product-wide locks. |
| Delivery drafts | Receive Delivery page resumes/edits/approves status `draft`, displays status `received`; Dashboard counts/navigates only status `draft`; Product and Inventory operations use active drafts for locks. |
| Activity events | Activity page filters and displays event payload snapshots and details. It does not reconstruct names from current Product/Inventory, though its labels currently imply session-only history. |
| Completed Sales | Reducer retains the list, but no current page is passed `ApplicationState.sales`. Sale details can be shown through `sale.completed` Activity snapshots. |

The current loaders and pages do not make Sales, Delivery, Product, or Inventory changes durable. Mapping these records into state is a read operation only.
