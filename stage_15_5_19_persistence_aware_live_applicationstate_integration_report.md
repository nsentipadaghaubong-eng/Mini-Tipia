# Stage 15.5.19 — Persistence-Aware Live ApplicationState Integration

## Verdict

**Stage 15.5.19 is complete.** After successful database initialization, snapshot loading, and hydration, the normal Mini-Tipia interface now mounts with the hydrated domain state. The persistence-aware hydration model remains available separately to the live interface. An empty SQLite snapshot opens an empty workspace without demo Products or Inventory.

This is a read-only startup integration. Workflow edits remain in-memory only; Stage 15.6 must implement and verify write persistence.

## Worktree preservation

The initial worktree contained pre-existing unstaged changes and numerous untracked persistence, migration, test, and report files. No staged changes were shown. Those files were preserved; no reset, cleanup, revert, or destructive Git operation was performed. Changes unrelated to this stage were not edited.

## Startup architecture and behavior

Before this stage, successful startup rendered the temporary “SQLite data loaded” verification screen and did not expose the normal business interface.

The live startup path is now:

1. `App` calls the existing `loadApplicationStateHydration` coordinator.
2. The coordinator awaits `initializeDatabase`, loads the eight collections through `loadApplicationData`, and creates the validated hydration model.
3. `App` projects available domain values from the hydration model into an `ApplicationState`.
4. `App` retains both the projected state and the complete hydration model in its ready state, then mounts `WorkflowApp` with both.
5. `WorkflowApp` initializes its reducer from the supplied hydrated `ApplicationState`; it no longer constructs its own demo-backed initial state.

Initialization, data-loading, and hydration errors continue to be surfaced in the explicit retryable startup error state. Loading keeps all workflows unavailable. The normal database was not launched, inspected, or modified during this stage; runtime integration was verified using the mocked startup boundary and existing isolated persistence tests.

## Empty data and persistence-only records

An empty successful hydration projects to empty collections and mounts the standard interface. The Products and Inventory pages show their normal empty states; the startup path does not call `createInitialApplicationState` and does not inject demo records.

The complete hydration model, including original persistence DTOs, is passed to `WorkflowApp` separately from the domain `ApplicationState`. Persistence-only historical records are not coerced into invalid domain values; the interface shows a small count of retained persistence-only records. When an active persisted draft has no safe domain projection, the interface reports that condition and makes its workflow content inert to protect draft locks.

## In-memory changes and persistence limitations

The live interface continues using existing reducers and business workflows. A status message explicitly says that changes made in the current session remain in memory and are not saved to SQLite. There are no INSERT, UPDATE, DELETE, or workflow persistence paths in this stage. Reducer changes, including Sales and Receive Delivery approvals, do **not** survive application restart.

Workflows not yet SQLite-persistent include:

- Product creation, update, and deletion.
- Inventory adjustments and stock/batch changes.
- Sales draft changes and sale approval.
- Receive Delivery draft changes, cancellation, and approval.
- Activity events generated by those workflow changes.

No business rules or workflow implementations were changed for this integration.

## Database and migration safety

No database was opened or modified by this stage. The normal database was not reset, seeded, deleted, or migrated. No schema or migration files, migration ledger entries, or checksum verification logic were changed. The new startup projection is read-only.

## Remaining limitation

This stage does not prove a live launch against the normal database, and it does not make workflow changes persistent. Stage 15.6 remains necessary for safe, verified write integration.
